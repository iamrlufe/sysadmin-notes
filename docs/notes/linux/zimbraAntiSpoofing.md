# Анти-спуфинг собственного домена на Zimbra MTA (Postfix)

Инструкция описывает, как запретить приём писем с адресом отправителя на собственном домене, если такие письма приходят из интернета без SMTP-авторизации. Реализация — через `smtpd_restriction_classes` в Postfix (MTA Zimbra), с сохранением работы легитимной почты.

## Проблема

Мониторинг обнаруживает письма вида:

```text
From: user@example.com
```

которые приходят из внешнего интернета, с IP отправителя из разных стран.

Первое впечатление — компрометация учётных записей. Но проверка учёток показывает, что они не взломаны. Реальная причина — **spoofing**: злоумышленник просто указывает в SMTP-диалоге

```text
MAIL FROM:<user@example.com>
```

и отправляет письмо напрямую на почтовый сервер по `25/tcp`, не проходя никакой авторизации.

## Что показала диагностика логов

- Подключений через веб-интерфейс с подозрительных IP **не было**.
- Это были подключения `postfix/smtpd` — то есть входящий SMTP на 25 порту.
- Отсутствовал `sasl_username=` — отправитель **не авторизовался**.
- Часть писем спам-фильтр отклонял как спам, часть — доходила до пользователей.

Характерный пример из лога:

```text
client=unknown[external-ip]
from=<user@sub.example.com>
to=<user@sub.example.com>
```

Письмо якобы отправлено пользователем самому себе с внешнего IP без авторизации — классический признак спуфинга, а не взлома.

!!! tip "Быстрый критерий"
    Нет `sasl_username=` в строке `postfix/smtpd`, а `from=` — на вашем домене → это подделка отправителя, а не скомпрометированный ящик.

## Почему SPF/DMARC не решают проблему полностью

SPF и DMARC говорят **чужим** почтовым серверам, что делать с письмами от вашего домена. Собственный входящий сервер эти записи, как правило, сам себе не проверяет. Поэтому цепочка

```text
злоумышленник → ваш MTA → From: user@example.com
```

может пройти, если спам-фильтр не сочтёт письмо достаточно подозрительным.

## Архитектура проблемы

```text
             Интернет
                │
                │ SMTP :25
                ▼
        ┌───────────────┐
        │  MTA (Postfix) │
        └───────┬───────┘
                │
         From: user@example.com
                │
                ▼
          Спам-фильтр
                │
        spam score недостаточен
                │
                ▼
          Ящик пользователя
```

MTA не говорит на SMTP-уровне: «если внешний сервер пытается отправить письмо от имени моего собственного домена — отклонить его». Поэтому часть spoof-писем доходит до пользователей.

## Ключевая сложность решения

Наивное решение — просто добавить домен в карту отклонений с жёстким `REJECT` — **ломает легитимную почту**: авторизованные пользователи и внутренняя сеть тоже отправляют письма с `From:` на собственном домене, и такое правило отклонит и их.

Правильный подход — **условный reject**: разрешить, если отправитель авторизован (SASL) или находится во внутренней доверенной сети, и только в остальных случаях отклонять.

## Решение: Postfix restriction_class

### 1. Определить restriction class

В конфигурационном шаблоне MTA (у Zimbra — `zmconfigd.cf`, в секции, которая генерирует `smtpd_restriction_classes`) добавляется:

```text
smtpd_restriction_classes = spoof_own_domain
spoof_own_domain = permit_mynetworks, permit_sasl_authenticated, reject
```

Смысл: если отправитель из доверенной сети (`mynetworks`) или прошёл SMTP-авторизацию (`sasl_authenticated`) — разрешить. Иначе — отклонить.

### 2. Включить проверку через check_sender_access

В цепочку `smtpd_sender_restrictions` добавляется:

```text
check_sender_access <тип_карты>:<путь_к_карте>
```

### 3. Карта доменов → restriction class

В карте (например, `postfix_reject_sender`) домен указывается **не** с жёстким `REJECT`, а со ссылкой на restriction class:

```text
example.com spoof_own_domain
```

!!! note "Поддомены наследуются автоматически"
    При доменном поиске Postfix ищет ключ прогрессивно — от наиболее специфичного к менее специфичному (`sub.example.com` → `example.com` → `com`). Одна запись для корневого домена покрывает все поддомены, перечислять каждый явно не нужно. Подтверждено практическим тестом.

## Порядок тестирования

Без этого порядка легко сломать прод.

1. **Бэкап** текущей конфигурации до любых изменений.
2. Внести правку restriction class, применить и проверить (`postconf -n` или аналог), что она реально подхватилась.
3. Сначала протестировать на **фиктивном, безопасном домене** (не на боевом), чтобы убедиться, что механизм в принципе работает.
4. Тест делать строго **снаружи доверенной сети и без авторизации** — иначе `permit_mynetworks` / `permit_sasl_authenticated` сработают раньше и ничего не покажут.
5. Довести SMTP-диалог до команды `RCPT TO`, не останавливаться на `MAIL FROM`. Многие MTA по умолчанию откладывают reject именно до этого шага (`smtpd_delay_reject = yes`), поэтому ответ на `MAIL FROM` может быть `250 Ok`, даже если транзакция уже помечена на отклонение.
6. Только после успешного теста на фиктивном домене — перенести правило на боевой домен.
7. Проверить три сценария: спуфинг с внешнего неавторизованного адреса отклоняется; легитимная авторизованная/внутренняя отправка проходит без изменений; поддомены тоже защищены за счёт наследования.
8. Смотреть **реальный** лог-файл MTA — события `postfix/smtpd` могут писаться в отдельный syslog-файл, а не в агрегированный лог почтовой платформы.

## Проверочный чек-лист

- [ ] Сделан бэкап конфигурации MTA
- [ ] `smtpd_restriction_classes` содержит `spoof_own_domain`
- [ ] `spoof_own_domain` = `permit_mynetworks, permit_sasl_authenticated, reject`
- [ ] `check_sender_access` добавлен в `smtpd_sender_restrictions`
- [ ] Конфигурация реально применилась (проверено выводом `postconf -n`)
- [ ] Механизм проверен на фиктивном домене снаружи, без авторизации, до `RCPT TO`
- [ ] Правило перенесено на боевой домен
- [ ] Спуфинг извне отклоняется
- [ ] Легитимная отправка (SASL / mynetworks) проходит
- [ ] Поддомены защищены одной записью корневого домена
- [ ] Проверен нужный лог-файл `postfix/smtpd`

## Частые ошибки

- **Жёсткий `REJECT` вместо restriction class** — отклоняет и собственных авторизованных пользователей.
- **Тест изнутри сети или с авторизацией** — срабатывает `permit_*`, и кажется, что правило не работает.
- **Остановка на `MAIL FROM`** — из-за `smtpd_delay_reject = yes` там будет `250 Ok`, reject придёт только на `RCPT TO`.
- **Правка сразу боевого домена** — ошибка в синтаксисе карты или класса сразу бьёт по всей почте домена.
- **Проверка не того лог-файла** — события есть, но ищутся не там, где пишутся.
- **Расчёт только на SPF/DMARC** — они управляют поведением чужих серверов, а не вашего входящего MTA.

## Итог

- Анти-спуфинг реализован через **условный** restriction class, а не через жёсткий `REJECT` — это критично для сохранения легитимной почты.
- Одна запись домена в карте покрывает все поддомены.
- Пошаговая проверка (тестовый домен → боевой домен, `MAIL FROM` → `RCPT TO`) позволяет внедрить изменение без риска сломать доставку.
